You are setting up a development environment for the project in the current working directory **inside the container you are already running in**. The container exists and the OS is already chosen — your job is to make sure `/aiab/setup.sh` contains the commands that install the toolchain and dependencies on top of it so the project can be built, run, and tested here, and to run that script when (and only when) the user says so.

`/aiab` is a persistent host-side directory mounted into every container for this project directory, so `/aiab/setup.sh` survives container recreation: after a container is deleted and recreated, running this command and confirming is all it takes to restore the dev environment. (On the host the file lives under `~/.local/share/aiab/dirstate/`, so the user can also edit it from outside the container.)

**Never run the script — or any setup commands — without the user's explicit go-ahead.**

## 0. Check for an existing script

If `/aiab/setup.sh` already exists, show its contents and ask the user whether to:

- **run it** — run `bash /aiab/setup.sh`, then the project's verification command (test suite, lint, a "hello world" run), and report the results;
- **edit it first** — apply the changes they describe (or wait while they edit the file themselves, from inside the container or on the host) and ask again;
- **regenerate it** — continue below as if it did not exist.

If `/aiab` does not exist, this container predates the state mount (or isn't an aiab container): do steps 1 and 2, present the commands as a copy-pasteable block instead of writing a script, and run nothing.

## 1. Discover the documentation

Read whatever the project actually provides. Look for (and don't assume all exist):

- `README*`, `CONTRIBUTING*`, `DEVELOPING*`, `HACKING*`, `INSTALL*`
- A `docs/` directory — especially pages about "getting started", "development", "setup", "build", "contributing"
- Any existing containerization or CI setup, treated as a *source of setup steps* (not as something to reproduce as an image): `Dockerfile*`, `.devcontainer/`, `docker-compose*.y*ml`, `Containerfile`, and CI workflows under `.github/workflows/` (these often encode the canonical setup steps)
- Dependency / toolchain manifests that reveal the runtime and version: `package.json` + lockfiles, `pyproject.toml`/`requirements*.txt`/`uv.lock`/`poetry.lock`, `go.mod`, `Cargo.toml`, `Gemfile`, `pom.xml`/`build.gradle`, `.tool-versions`/`.nvmrc`/`.python-version`, `Makefile`, `Taskfile.y*ml`

Prefer instructions written in the docs over inferences from manifests. When the docs and the manifests disagree, trust the docs but note the discrepancy.

## 2. Determine the setup

Assume a generic Linux container with a normal base toolchain (a shell, a package manager, network access) but nothing project-specific installed yet. From what you read, work out:

- **Language runtime / toolchain** — what to install and the *specific version* the project targets (pin it; don't default to "latest"). Check what's already present before reinstalling.
- **System packages** — OS-level deps the docs mention (build tools, libs, headers), installed via the container's package manager.
- **Package manager** — how project dependencies are installed (e.g. `npm ci`, `uv sync`, `poetry install`, `go mod download`, `bundle install`).
- **Project dependency install** — the exact commands the docs prescribe.
- **Build / codegen steps** — anything required before the app runs.
- **Env vars, services, ports** — anything needed at runtime (databases, env files, exposed ports), with the caveat that external services may not be reachable from inside the container.
- **Verification** — the command the docs use to confirm a working setup (test suite, lint, a "hello world" run). This is run after the script, not from inside it.

## 3. Write the script and present it

Write the setup commands to `/aiab/setup.sh`:

- Start with `#!/bin/bash` and `set -eux`, then a header comment saying the script was generated by the setup-container agent, when, and from which docs.
- A brief `# comment` before each logical group explaining what it does and which doc it came from. Pin versions. The script runs from the repo root inside the container.
- Prefer commands that are safe to re-run — the same script will be run again in freshly recreated containers, and sometimes in one where it already half-succeeded.

Then output, in this order:

1. **Summary** — one short paragraph: detected language/runtime + version and package manager, and where you found the authoritative instructions (cite the files).
2. **The script** — the full contents of `/aiab/setup.sh` as written.
3. **Run & verify** — the command(s) to build/start the app and to confirm the environment works after the script has run.
4. **Gaps & assumptions** — bullet anything the docs didn't specify that you had to assume, and anything the user should double-check (secrets, external services, anything that may not be available inside the container).

Finally, ask the user whether to run it now or edit it first (same options as step 0).

Keep it faithful to the repository. If you genuinely can't find setup documentation, say so plainly and list what you'd need — don't write a script of fabricated commands.
